# Звіт про реалізацію відновлення пароля (Supabase forgot password / password recovery)

> Статус: **реалізовано**. `npm run build` проходить без помилок.
> Зміни **не закомічені** і **не запушені** в Git (як і вимагалося).
> Попередні звіти: `MiMo_AUTH_PLAN.md`, `MIMO_AUTH_IMPLEMENTATION.md`.

---

## 1. Що реалізовано

| Вимога | Реалізація |
|---|---|
| Запит листа для скидання пароля | Сторінка `/forgot-password` (форма email) → `supabase.auth.resetPasswordForEmail(email, { emailRedirectTo: window.location.origin })`; після успіху — панель «перевірте пошту» з повторним надсиланням |
| Посилання з листа → новий пароль | PKCE-обмін встановлює recovery-сесію; guard перенаправляє на `/reset-password`, де форма «новий пароль + підтвердження» → `supabase.auth.updateUser({ password })` |
| Валідація | Email — та сама регулярка, що й на `/login`; пароль — ≥6 символів + збіг підтвердження (як у `/register`); все локалізовано українською |
| Loading-стани | `submitting`/`resending`: disabled-кнопки й поля, `LoadingSpinner` у кнопках (як у наявних формах) |
| Повідомлення про успіх | `AppAlert type="success"`: лист надіслано (з email), пароль оновлено; `type="info"` для повторного надсилання |
| Дружні помилки | Нові мапінги в `authErrors.js`: протермінована/відсутня сесія, «новий пароль має відрізнятися», користувача не знайдено, недозволений redirect, `Auth session missing`; rate-limit і мережа вже були |
| Маршрутизація по всьому процесі | Guard на **першій** навігації: вдалий обмін + маркер recovery → `/reset-password`; невдалий обмін + маркер → `/forgot-password?recoveryFailed=1`; поведінка для підтвердження пошти **не змінилася** |
| Збереження наявного функціоналу | Усі зміни адитивні: гілки guard активуються лише за наявності маркера; логін/реєстрація/вихід/підтвердження працюють як раніше |
| Відповідність конвенціям | 4-пробільний відступ у JS, 2-пробільний у SFC, `<script setup>`, ті самі Tailwind-класи форм, український інтерфейс, **без нових залежностей** |

## 3. Модифіковані файли

| Файл | Зміни |
|---|---|
| `src/stores/auth.js` | Маркер відновлення в localStorage (`planner:password-recovery-request`, TTL 24 год) + хелпери `mark/hasRecent/clearRecoveryRequested`; нові дії `requestPasswordReset(email)`, `updatePassword(password)`; `login()`/`register()` очищують маркер при успіху; повернення дій у store |
| `src/router/index.js` | Маршрути `/forgot-password` (`guestOnly`) і `/reset-password` (публічний); у `beforeEach` на першій навігації — обробка recovery-посадки (успіх → `/reset-password`, невдача → `/forgot-password?recoveryFailed=1`) |
| `src/lib/authErrors.js` | 4 нові блоки мапінгу (сесія/refresh, інший пароль, користувач, invalid redirect) **перед** `validation_failed`; виправлено regex `code[ _]challenge` (GoTrue надсилає `code_challenge` з підкресленням — старий regex не збігався) |
| `src/lib/redirect.js` | `/forgot-password` додано до `BLOCKED_PATHS` (анти-loop для guest-only цілі, як `/login`, `/register`) |
| `src/views/LoginView.vue` | Посилання «Забули пароль?» між полем пароля і кнопкою входу (зберігає `redirect`) |

**Без змін:** `src/lib/supabase.js` (конфіг `pkce`/`detectSessionInUrl` уже правильний), `src/main.js`, `src/App.vue`, `.env.local`, налаштування Supabase Dashboard.

## 4. Ключові архітектурні рішення

1. **`emailRedirectTo = window.location.origin` — той самий рядок, що й у `register`.** Лист відновлення повертає на корінь застосунку, тобто використовує **ту саму запису Redirect URLs**, що й підтвердження реєстрації: жодних нових вимог до Dashboard і жодного ризику «Invalid redirect URL» для нового шляху (напр. `/reset-password` міг не потрапити в allowlist).

2. **Маркер відновлення в localStorage — надійний сигнал посадки.** І URL, і подія `PASSWORD_RECOVERY` можуть бути відсутніми: auth-js прибирає `code` з URL через `history.replaceState` **одразу після успішного обміну** (може раніше, ніж vue-router розпарсить початкову локацію), а `PASSWORD_RECOVERY` надсилається з черги ініціалізації конструктора клієнта — підписка store реєструється пізніше й може її пропустити. localStorage: (а) спільний між вкладками (поштовий лінк часто відкривається в новій вкладці), (б) переживає переадресацію поштою, (в) не залежить від таймінгів мережі. Маркер пишеться **до** мережевого виклику (випадок «лист надіслано, відповідь загубилася»), споживається guard-ом при посадці, TTL 24 год.

3. **False positives виключені очищенням маркера.** Запит може зробити лише розлогінений користувач (`guestOnly`), а будь-яке подальше успішне автентифікування проходить через `login()`/`register()` — обидві дії чистять маркер. Тому «залогінений, але зі свіжим маркером» практично неможливо, крім справжньої recovery-посадки. Маркер також чиститься після успішного `updatePassword`.

4. **Guard розрізняє успіх/невдачу обміну через `isAuthenticated` після `await auth.initialize()`** (ініціалізація гарантовано чекає повний PKCE-обмін): `code`/`error` у query + автентифікований = успіх; без сесії = невдача. Обмін відбувається лише при повному завантаженні — тому вся логіка обмежена `isFirstNavigation`, як і раніше. Поведінка без маркера (підтвердження пошти, чужий браузер) **дослівно збережена**.

5. **`/reset-password` — публічний маршрут** (без `requiresAuth`): протерміноване посилання має показати дружній стан «посилання недійсне» на самій сторінці, а не відскок на `/login`. Без `guestOnly`: сторінка працює і для звичайної зміни пароля, якщо користувач зайде на неї напряму.

6. **`/forgot-password` — `guestOnly`** (консистентно з `/login`, `/register`) і заблокований як ціль `redirect` у `redirect.js`.

7. **Store повертає готові повідомлення, а не винятки** — той самий контракт `{ ok, error? }`, що й у наявних діях; store лишається без імпорту router (навігацію роблять view/guard).

8. **Оновлення пароля без примусового перелогіню** — `updateUser({ password })` зберігає recovery-сесію; користувач лишається увійшеним (стандартна поведінка Supabase).

9. **Порядок мапінгів у `authErrors.js`**: повідомлення-regex для «new password should be different» стоїть **перед** `validation_failed`, бо GoTrue може повертати цю помилку саме з кодом `validation_failed`.

## 5. Відомі обмеження та невирішені питання

1. **Залежність від Redirect URLs у Dashboard** (не змінювалося): лист відновлення використовує origin застосунку — **та сама вимога, що й для реєстрації** (напр. `http://localhost:5173/` для розробки). Якщо GoTrue відхилить `redirectTo`, користувач побачить «Не вдалося підготувати лист відновлення. Спробуйте пізніше.» (замаплено).
2. **Посилання працює лише в тому самому браузері** (PKCE-верифікатор у localStorage) — за дизайном. Інший браузер/інший пристрій: обмін не відбувається → стандартний банер на `/login` (контекст «підтвердження пошти», а не «відновлення» — маркер недоступний на іншому пристрої). На тихому пристрої зі свіжим маркером — точне повідомлення на `/forgot-password`.
3. **Протермінований маркер (>24 год)**: клік у дуже старе посилання покаже загальний `confirmFailed` на `/login`, а не recovery-повідомлення (TTL вичерпано). Практично не досяжно — сам лінк живе ~1 год.
4. **Маркер зберігається у відкритому localStorage** (лише мітка часу, без секретів); захищено try/catch — недоступний storage деградує до «без маркера», не ламаючи потік.
5. **`/reset-password` доступний будь-якому автентифікованому користувачу** (фактично сторінка зміни пароля) — навмисно, шкоди не несе.
6. **Косметика:** після «назад» з `/reset-password` на посадку в адресному рядку може лишитися старий `?code` (SPA-навігація повторного обміну не робить) — не впливає на роботу.
7. **`PASSWORD_RECOVERY` не використовується для маршрутизації** (таймінг підписки) — лише для оновлення стану сесії через наявний загальний обробник.
8. **Немає автоматизованих тестів** — test-інфраструктури в проєкті немає (як і раніше). Хелпери перевірено ad-hoc у Node (див. §6); рантайм у браузері потребує ручного тестування (див. §7).
9. **Наявні проблеми проєкту, свідомо не виправлені** (поза скоупом): неправильний контент `PlannerView.vue`, порожній `SettingsView.vue`, шаблонний CSS у `style.css`, мертвий `HelloWorld.vue`, відсутність лінтерів.

## 7. Що слід протестувати вручну (потрібні робочі налаштування Supabase)

Перед тестуванням: Redirect URLs містять origin застосунку (`http://localhost:5173/`), PKCE flow увімкнено (як для реєстрації).

### Новий потік
1. **Запит:** `/login` → «Забули пароль?» → `/forgot-password?redirect=…` → порожній/невалідний email → повідомлення; валідний → панель «Ми надіслали лист…» + кнопка «Надіслати лист ще раз» працює.
2. **Лист:** приходить на пошту; посилання відкривається **в тому самому браузері** → одразу потрапляємо на `/reset-password` (форма з email акаунта), **не** на `/` і **не** на `/login`.
3. **Валідація форми:** пароль <6 символів, незбіг підтвердження → свої повідомлення; успіх → «Пароль успішно оновлено.» → «Перейти на головну» → dashboard.
4. **Новий пароль діє:** вийти → увійти **новим** паролем OK; **старим** — «Невірний email або пароль.».
5. **Той самий пароль ще раз** (якщо сервер забороняє) → «Новий пароль має відрізнятися від поточного.».
6. **Протерміноване/повторне використане посилання** (той самий браузер, маркер ще свіжий) → `/forgot-password` з банером «Посилання для відновлення пароля недійсне або застаріло…» і кнопкою запиту нового листа.
7. **Чужий браузер/інкогніто** (без маркера й верифікатора) → `/login` з наявним банером `confirmFailed` (поведінка як для підтвердження пошти).
8. **`/reset-password` вручну без сесії** → стан «посилання недійсне» + «Запросити новий лист» + «Увійти» (не редірект на `/login`).
9. **Rate limit:** кілька запитів підряд → «Забагато спроб…».
10. **Мережа вимкнена:** запит листа → «Не вдалося зв'язатися з сервером…», без крашу; форма не застрягає в disabled.

### Регресія наявного функціоналу
11. **Реєстрація + підтвердження:** `/register` → лист → клік у тому ж браузері → сесія → dashboard (маркер відсутній або очищений — **без** редіректу на `/reset-password`).
12. **Сценарій «запитав скидання, потім залогінився»:** `/forgot-password` → запит → повернутися → `/login` → вхід → наступне перезавантаження → dashboard, **не** `/reset-password`.
13. **Вхід/вихід, глибокий `redirect`:** `/planner` розлогіненим → `/login?redirect=%2Fplanner` → вхід → `/planner`; guest-only редіракти; open-redirect (`/login?redirect=//evil.com` → `/`).
14. **Hard reload** на `/settings` залогіненим → без flash на `/login`; вихід в іншій вкладці → редірект на `/login`.
15. **`/forgot-password` залогіненим** → одразу редірект на `/` (або безпечний `redirect`); `?redirect=/forgot-password` санітизується в `/`.
16. **Швидкий подвійний клік** по кнопках запиту/збереження → один запит (disabled).

# Supabase Auth (email/password) — реалізація та аудит

> Документ фіксує план, фактичну реалізацію та результат аудиту авторизації в `task-planner`.
> Реалізація: 16 листопада 2026. Аудит повторної реєстрації: 18 листопада 2026.
> Google OAuth і відновлення пароля свідомо відкладені (див. розділ 9).
>
> **Важливо:** аудит був режимом аналізу. Вихідний код, налаштування Supabase і `.env.local`
> не змінювалися. У розділах 6–8 зафіксовано висновки та рекомендації, а не виконані зміни.

## 1. Мета

- Додати email/password авторизацію через Supabase Auth.
- Supabase — джерело істини для сесії, токенів і підтвердження email.
- Pinia — реактивний стан сесії для UI.
- Vue Router — захист приватних маршрутів.

## 2. Вимоги

1. Pinia auth store: реєстрація, вхід, вихід, відновлення сесії.
2. Сторінки входу та реєстрації з валідацією, помилками й станами завантаження.
3. Захист маршрутів через Vue Router.
4. `App.vue` відображає стан авторизації та кнопку виходу.
5. Підтвердження email після реєстрації.
6. Коректна ініціалізація сесії: без дублювання підписок і зайвих редиректів.
7. JavaScript, Vue 3 Composition API, без зайвих абстракцій.

## 3. Фактична реалізація

**Нові файли:**

| Файл | Призначення |
|---|---|
| `src/stores/auth.js` | Pinia store авторизації (setup-стиль) |
| `src/lib/authErrors.js` | Переклад типових помилок Supabase Auth українською |
| `src/views/LoginView.vue` | Сторінка входу |
| `src/views/RegisterView.vue` | Сторінка реєстрації + екран «Підтвердьте email» |
| `src/views/NotFoundView.vue` | Сторінка 404 |

**Змінені файли:**

| Файл | Зміни |
|---|---|
| `src/router/index.js` | Маршрути `/login`, `/register`, 404; `meta`; глобальний guard |
| `src/App.vue` | Навігація залежно від стану: email + «Вийти» / «Увійти» + «Зареєструватися» |
| `src/lib/supabase.js` | Толерантність до URL із суфіксом `/rest/v1/` (значення `.env.local` не змінювалося) |

**Ключові рішення:**

- `initialize()` через `initPromise`: `getSession()` і підписка `onAuthStateChange`
  виконуються рівно один раз навіть при паралельних викликах із router guard.
- Guard чекає завершення ініціалізації — немає «миготіння» редиректами після F5.
- `redirect` із query захищений від open redirect (дозволені лише шляхи, що починаються з `/`).
- Помилки Supabase у перекладі `authErrors.js`; невідомі повідомлення показуються як є.
- Нових залежностей не додавалося; база даних не змінювалася.

## 4. Налаштування Supabase Dashboard (потребує ручної перевірки)

1. **Authentication → Sign In / Providers → Email** — провайдер Email увімкнено.
2. **Authentication → URL Configuration**:
   - **Site URL**: `http://localhost:5173` для деву (продакшен-домен — пізніше).
   - **Redirect URLs**: додати `http://localhost:5173/**`, інакше посилання з листа не відкриється.
3. **Authentication → Emails** — шаблон «Confirm signup» має використовувати
   `{{ .ConfirmationURL }}` (стандартно так).
4. Бажано прибрати суфікс `/rest/v1/` зі значення `VITE_SUPABASE_URL`: має бути
   корінь проєкту `https://<ref>.supabase.co`. Код прощає обидва варіанти,
   але чисте значення — правильний варіант. У межах аудиту значення не перевірялося й не змінювалося.

## 5. Сценарій ручного тестування

1. **Реєстрація:** `/` → редірект на `/login`. «Зареєструватися» → реальна пошта +
   пароль (6+ символів) → екран «Підтвердьте email».
2. **Підтвердження:** відкрити лист → перейти за посиланням →
   сесія підтягується з URL (implicit flow), користувач залогінений.
3. **Вихід:** кнопка «Вийти» → `/login`, пункти меню зникають.
4. **Вхід:** неправильний пароль → «Неправильна пошта або пароль»;
   правильні дані → перехід на `/`. саме неправильний пароль дає `400` на `/auth/v1/token`.
5. **Відновлення сесії:** на `/planner` натиснути **F5** → користувач залишається
   залогіненим, без кидка на `/login`.
6. **Захист маршрутів:** після виходу відкрити вручну `/planner` →
   редірект на `/login?redirect=/planner`; після входу — повернення на `/planner`.
7. **Новий випадок для перевірки (додано аудитом):** повторна реєстрація з уже
   підтвердженою поштою → поточний UI показує «Ми надіслали лист», але лист не приходить.
   Детально — розділ 6.
8. **Перевірка збірки:** `npm run build` — успішно, без помилок.

## 6. Аудит: повторна реєстрація підтвердженої email-адреси

### 6.1 Симптом

- Перша реєстрація, підтвердження email і вхід працюють.
- Повторна реєстрація тієї самої **вже підтвердженої** адреси: застосунок показує
  «Ми надіслали лист для підтвердження», але лист не приходить.
- У DevTools раніше спостерігалися `POST /auth/v1/token` зі статусом `400 Bad Request`.
- Відновлення сесії, вихід і синхронізація вкладок працюють успішно.

### 6.2 Що робить код

| Місце | Спостереження |
|---|---|
| `src/stores/auth.js:47-51` (`signUp`) | Повертає `{ needsEmailConfirmation: !data.session }`. Відсутність сесії ототожнюється з «потрібне підтвердження». |
| `src/stores/auth.js:53-57` (`signIn`) | `signInWithPassword`, помилки не ковтаються, сесія встановлюється напряму. Саме звідси йде `/auth/v1/token?grant_type=password`. |
| `src/stores/auth.js:21-44` (`initialize`) | `initPromise` гарантує одну ініціалізацію; `getSession()` → підписка → `ready = true`. Логіка загалом коректна. |
| `src/lib/authErrors.js` | Мапить відомі повідомлення; зокрема `User already registered` → «Користувач із такою поштою вже зареєстрований», а `Email not confirmed` обіцяє надісланий лист. |
| `src/views/RegisterView.vue:39-43, 59-63` | Показує екран із ствердженням «Ми надіслали лист…» для будь-якого успішного `signUp` без сесії. |

### 6.3 Чи це очікувана поведінка Supabase — так

Згідно з JSDoc `@supabase/auth-js@2.119.0` для `auth.signUp()` та серверним кодом
Supabase Auth (`internal/api/signup.go`):

- При увімкненому **Confirm email** новий користувач повертає `user` і `session: null`.
- При вимкненому **Confirm email** повертаються і `user`, і `session`.
- Повторний `signUp` для **вже підтвердженого** користувача:
  - якщо увімкнені Confirm email і Confirm phone → повертається **обфускований/fake**
    об’єкт користувача (HTTP `200`);
  - якщо будь-яке з підтверджень вимкнене → помилка `User already registered` (`422`).
- Серверний шлях для першого випадку: `UserExistsError` → audit-log
  `UserRepeatedSignUpAction` → `sanitizeUser()` → `200 OK`. Очищений об’єкт має
  випадковий `id`, `identities: []`, `confirmed_at: null`, `confirmation_sent_at = now`.
  **Лист не надсилається.** Це навмисний захист від user enumeration.
- Повторний `signUp` для **не підтвердженого** email — лист надсилається знову,
  повертається реальний `user` без сесії.

Висновок: відсутність листа — коректна поведінка сервера; хибним є UI-висновок застосунку.

### 6.4 Хибна інтерпретація відповіді `signUp`

Підтверджено. `data.session === null` означає лише «сесії немає», а не «лист надіслано».
Цей самий стан виникає і для нового користувача, і для fake-відповіді на повторну
реєстрацію. Маркер `data.user?.identities?.length === 0` існує, але використовувати
його для повідомлення «ви вже зареєстровані» не можна — це розкриє існування акаунта.

### 6.5 `400 Bad Request` на `/auth/v1/token`

`signUp` завжди іде на `/auth/v1/signup` і **ніколи** не викликає `/token`, тож ці `400`
не є наслідком реєстрації.

| Джерело | Запит | Типова причина `400` |
|---|---|---|
| `signInWithPassword` | `grant_type=password` | неправильний пароль/email, email не підтверджено, користувач забанений |
| Автооновлення в auth-js | `grant_type=refresh_token` | прострочений/вже використаний refresh token, ротація між вкладками, revoked session |
| `verifyOtp` / PKCE | `grant_type=pkce` | невалідний код або code verifier |

Найімовірніше джерело — тест неправильного пароля з розділу 5 (пункт 4):
повідомлення `Invalid login credentials` і є очікуваним. Для уточнення в DevTools слід дивитися
`grant_type` у payload і `msg`/`error_code` у відповіді, не виводячи самі токени.

### 6.6 Безпечне повідомлення для користувача

Рекомендована нейтральна фраза (однакова для всіх успішних `signUp` і для випадку
з помилкою `User already registered`, якщо вона колись з’явиться):

> **«Якщо акаунт із цією адресою ще не створено, ми надішлемо лист для підтвердження.
> Перевірте пошту, включно з папкою «Спам». Якщо ви вже підтверджували email — просто увійдіть.»**

Вона не стверджує, що лист точно надіслано, і не розкриває, чи існує акаунт.

### 6.7 Інші зауваження

- `src/lib/authErrors.js`: рядок із `User already registered` явно розкриває існування акаунта;
  рядок для `Email not confirmed` теж обіцяє надісланий лист.
- `src/stores/auth.js`: `signUp` не встановлює `session.value`, на відміну від `signIn`;
  покладається на подію auth-js. Працює, але крихко, якщо підписка ще не створена.
- Підписка `onAuthStateChange` створюється в `finally` після `getSession()` — події під час
  відновлення сесії пропускаються; стан усе одно синхронізується з `getSession()`, ризик низький.
- Немає збереженого `unsubscribe` (актуально для HMR, у проді — ні).
- Немає обробки помилок confirmation-лінки (`error_description`, `access_denied`)
  і сценарію повторного надсилання листа (`resend()`).

## 7. Висновки

### 7.1 Підтверджені проблеми

1. `src/stores/auth.js:50` — хибна інтерпретація відповіді `signUp`:
   `!data.session` сприймається як ознака надісланого листа.
2. `src/views/RegisterView.vue:59-63` — UI стверджує надсилання, хоча сервер лист не надсилав.
3. `src/lib/authErrors.js` — повідомлення розкриває існування акаунта й необґрунтовано обіцяє лист.

### 7.2 Очікувана поведінка Supabase

- Повторний `sign_up` підтвердженого email при увімкненому Confirm email → `200` із
  obfuscated user (`identities: []`), без сесії й без листа.
- `signUp` іде на `/auth/v1/signup`, а не `/auth/v1/token`.
- `400` на `/token?grant_type=password` — нормальна відповідь на неправильні дані або
  не підтверджений email; `400` на `grant_type=refresh_token` — можлива при ротації чи
  простроченні сесії.

### 7.3 Гіпотези, які потребують додаткової перевірки

1. Який саме `grant_type` і `msg` було в тих `400` у DevTools — найімовірніше,
   тест неправильного пароля з плану ручних перевірок.
2. Чи виникали `400` під час F5 або роботи в кількох вкладках через оновлення refresh token.
3. Фактичні прапори Confirm email / Confirm phone і стан SMTP у Dashboard не перевірялися:
   висновок зроблено з поведінки коду, першого успішного сценарію та документації бібліотеки.

## 8. Рекомендовані наступні кроки (не застосовані в межах аудиту)

1. Замінити `{ needsEmailConfirmation: !data.session }` на нейтральний статус
   (наприклад `{ status: 'check_email' }`) без розрізнення новий/наявний акаунт.
2. Використати фразу з розділу 6.6 і прибрати з `authErrors.js` повідомлення,
   що розкриває існування користувача.
3. У `signUp` встановлювати `session.value = data.session`, якщо сесія повернулася.
4. Зберігати результат `onAuthStateChange` для коректного `unsubscribe`.
5. Додати обробку помилок confirmation-лінки та повторного надсилання листа.
6. Повторити DevTools-перевірку з фіксацією лише `grant_type` і `msg` (без токенів).

# Звіт про реалізацію аутентифікації (Supabase email/password)

> Статус: **реалізовано**. `npm run build` проходить без помилок.
> Зміни **не закомічені** і **не запушені** в Git (як і вимагалося).
> Попередній план: див. `MiMo_AUTH_PLAN.md`.

---

## 1. Що реалізовано

| Вимога | Реалізація |
|---|---|
| Реєстрація email/password з підтвердженням пошти | `signUp()` з `emailRedirectTo: window.location.origin`; після успіху — панель «перевірте пошту» з можливістю надіслати лист повторно (`resend({ type: 'signup' })`) |
| Вхід / вихід | `signInWithPassword()` / `signOut()` |
| Персистентність сесії | `persistSession: true`, `autoRefreshToken: true` (явно задано в `createClient`), сесія зберігається в localStorage, токен оновлюється мовчки |
| Стан аутентифікації в Pinia | Setup-store `src/stores/auth.js`: `user`, `session`, `initialized`, геттер `isAuthenticated`, дії `initialize/register/login/logout/resendConfirmation` |
| Protected та guest-only маршрути | `meta.requiresAuth` на `/`, `/planner`, `/settings`; `meta.guestOnly` на `/login`, `/register`; `router.beforeEach` guard |
| Редірект на початково запитувану сторінку після логіну | Guard зберігає `redirect=to.fullPath`; після успішного логіну/реєстрації view виконує `router.replace(getSafeRedirect(...))` |
| Зрозуміле повідомлення про помилки | `src/lib/authErrors.js` мапить коди/повідомлення Supabase на українські тексти; відображення через компонент `AppAlert` |
| Loading-стани | `submitting`/`resending` у формах (disabled + spinner), `loggingOut` у header, спінер під час відновлення початкової сесії (`initialized` gate у `App.vue`) |
| Відповідність конвенціям проєкту | 4-пробільний відступ у JS, 2-пробільний у SFC, `<script setup>`, Tailwind utility-класи, український текст інтерфейсу, без нових залежностей |

## 4. Ключові архітектурні рішення

1. **PKCE flow явно на клієнті.** У встановленому `@supabase/auth-js@2.119.1` дефолт — `flowType: 'implicit'`, тоді як сучасні проєкти Supabase за замовчуванням використовують PKCE. Задано `'pkce'` явно, щоб клієнт відповідав налаштуванням проєкту.
2. **Ініціалізація без гонки (race).** `initialize()` реєструє `onAuthStateChange` першим, а потім читає початковий стан через `getSession()`. За перевіреним джерелом `auth-js`, `getSession()` очікує `initializePromise` (повна ініціалізація: обмін кодом з URL + відновлення сесії зі сховища), тому його результат є авторитетним **незалежно від порядку** події `INITIAL_SESSION`. Це усуває класичний баг «logged-out flash / хибний редірект на `/login` при hard reload». Guard викликає `await auth.initialize()` (ідемпотентно) перед кожним рішенням.
3. **Усі зміни стану — через `onAuthStateChange`.** Покриває: перезавантаження, мовчазне оновлення токена, **вихід в іншій вкладці** (BroadcastChannel), приземлення підтвердження email. Store **не імпортує router** (навігацію роблять view) — виключено циклічні імпорти; `useAuthStore()` викликається всередині guard-колбеку, не на top-level.
4. **Store повертає готові повідомлення, а не винятки.** Дії повертають `{ ok, error?, errorCode?, needsConfirmation? }`, причому `error` уже локалізований через `getAuthErrorMessage`. Усі дії обгорнуті в `try/catch` — неочікуваний виняток (наприклад, заблокований storage) ніколи не «втече» у view без повідомлення.
5. **Санітизація redirect у одному місці.** `getSafeRedirect` приймає лише шляхи, що починаються з одного `/`, без `//`, без пробілів/табуляції/backslash (браузери видаляють `\t` з URL, що могло б перетворити `/\t/evil.com` на `//evil.com`), і ніколи не повертає на `/login`/`/register` (анти-loop). Використовується і guard-ом, і view.
6. **Обробка невдалого PKCE-обміну.** За перевіреним джерелом auth-js, `code` видаляється з URL (`history.replaceState`) **лише при успішному** обміні. Тому на **першій** навігації (повне завантаження сторінки) наявність `code`/`error` у query означає невдалий обмін (наприклад, лист відкрито в іншому браузері). Guard прибирає ці параметри й показує на `/login` зрозуміле повідомлення (`confirmFailed=1`). Перевірка обмежена першою навігацією, щоб майбутні власні `?code=`/`?error=` параметри маршрутів не зачіпалися.
7. **Надійний logout.** За дефолтним `scope: 'global'` auth-js видаляє збережену сесію **лише після успішної відміни на сервері** — при помилці мережі сесія «воскресла» б після перезавантаження. Реалізовано fallback: якщо `signOut()` завершився помилкою, викликається `signOut({ scope: 'local' })` (видаляє локальну сесію до мережевого запиту), а стан очищується в `finally` у будь-якому випадку.
8. **Захист при втраті сесії.** Watcher в `App.vue` на `isAuthenticated`: якщо сесія зникла на protected-сторінці (вихід в іншій вкладці, відкликаний/прострочений токен), користувач редіректиться на `/login?redirect=<поточна сторінка>`. Цей же watcher виконує навігацію після успішного logout — єдиний шлях навігації, без конкуруючих `router.replace`.
9. **Помилкові звернення захищені.** Guard для незахищеної цілі повертає `{ name: 'login', query: { redirect: to.fullPath } }` (повний шлях з query), для guest-only — `getSafeRedirect(to.query.redirect)`; loop виключено блокуванням `/login`, `/register` як цілі.

## 5. Відомі обмеження та невирішені питання

1. **Залежність від налаштувань Supabase Dashboard** (з коду змінити неможливо — не змінювалося):
   - Email provider увімкнено, **"Confirm email" ON** (інакше `needsConfirmation` ніколи не спрацює — сесія створюватиметься одразу);
   - **Redirect URLs** мають містити origin застосунку (для розробки — `http://localhost:5173/`), оскільки `emailRedirectTo: window.location.origin` передає його в лист;
   - **PKCE flow** увімкнено (дефолт проєкту) — має збігатися з `flowType: 'pkce'` клієнта.
   Невідповідність проявиться як помилка обміну при відкритті листа підтвердження (є дружнє повідомлення + порада відкрити в тому самому браузері).
2. **Підтвердження в іншому браузері/пристрої неможливе за дизайном PKCE** (code verifier зберігається лише в localStorage браузера, де відбулася реєстрація). Обробляється повідомленням `confirmFailed` та кнопкою повторного надсилання листа.
3. **Скидання пароля (forgot password) не реалізовано** — поза вимогами/скоупом (згідно з планом). Додається в той самий store через `resetPasswordForEmail` / `updateUser`.
4. **Помилка глобального logout за мережі:** локальна сесія цього пристрою очищується (fallback `local`), але відміна сесій на **інших** пристроях може не відбутися (сервер не відповів). У крайньому випадку (fallback теж зазнав невдачі, наприклад storage заблоковано) сесія може відновитися після перезавантаження.
5. **Немає автоматизованих тестів** — у проєкті відсутня test-інфраструктура (до реалізації теж). Чисті хелпери `getSafeRedirect`/`getAuthErrorMessage` перевірено ad-hoc у Node (25 кейсів — усі пройшли), але test suite не додавався (поза скоупом).
6. **Рантайм у браузері не тестувався автоматично** — у середовищі немає browser-автоматизації. Верифіковано: production build (усі 90 модулів трансформуються, імпорти резолвляться), компіляція SFC без попереджень, логіка хелперів. Поведінка навігації/сесій потребує ручного тестування (див. §7).
7. **Прапорець `isFirstNavigation`** скидається під час HMR у dev-режимі (незначно, лише розробка) і діє один раз на повне завантаження сторінки — це правильно, бо обмін PKCE відбувається лише при повному завантаженні.
8. **Наявні проблеми проєкту, свідомо не виправлені** (поза скоупом аутентифікації, зафіксовано в плані):
   - `PlannerView.vue` має неправильний контент (заголовок «Settings»), `SettingsView.vue` порожній;
   - залишковий шаблонний CSS Vite у `style.css` (глобальний `#app` з `text-align: center`, `h1` 56px) — нові форми інвалідові до нього через `text-left` та явні `text-3xl`;
   - мертвий `HelloWorld.vue`; відсутність лінтерів/formatting-конфігурації.
9. **Виробничий хост** для `createWebHistory` має мати SPA-fallback (глибокі лінки на `/login`); Vite dev server надає це автоматично.

## 7. Що слід протестувати вручну (потрібні робочі налаштування Supabase)

Перед тестуванням переконайтеся в Dashboard: "Confirm email" увімкнено; у Redirect URLs додано `http://localhost:5173/`; PKCE flow увімкнено.

1. **Реєстрація + підтвердження:** `/register` → панель «перевірте пошту» → лист приходить → клік у **тому ж браузері** → сесію створено → вхід у застосунок (без ручного логіну).
2. **Глибокий лінк після підтвердження:** розлогінений відкрити `/planner` → `/login?redirect=%2Fplanner` → зареєструватися (посилання зберігає `redirect`) → підтвердити пошту → потрапити на `/planner`.
3. **Невірний пароль** → «Невірний email або пароль.», кнопка знову активна, ввід не блокується назавжди.
4. **Вхід з непідтвердженим email** → конкретна помилка + кнопка «Надіслати лист підтвердження ще раз» працює (другий лист).
5. **Hard reload** на `/settings` залогіненим → залишається на `/settings`, **без** flash на `/login`.
6. **Guest-only:** залогінений відкриває `/login` або `/register` → одразу редірект на `/` (або безпечний `redirect`).
7. **Open redirect:** `/login?redirect=//evil.com`, `/?redirect=%2F%2Fevil.com`, `/login?redirect=/login` → потрапити на `/`, не на зовнішній сайт і без loop.
8. **Вихід:** кнопка «Вийти» → pending-стан → навігація перемикається на Увійти/Реєстрація → прямий вхід на `/settings` → редірект на `/login?redirect=%2Fsettings`.
9. **Вихід в іншій вкладці:** два таби залогінені → logout в табі A → таб B оновлює навігацію **і** редіректить із protected-сторінки на `/login`.
10. **Онлайн-статус:** логін з вимкненим інтернетом → повідомлення «Не вдалося зв'язатися з сервером…», без крашу.
11. **Подвійний submit:** швидкий подвійний клік по кнопці → один запит (кнопка disabled).
12. **Дублікат реєстрації** → «Користувач з таким email вже існує.»
13. **Rate limit:** кілька повторних надсилань листа підряд → повідомлення про обмеження.
14. **Невдалий обмін PKCE:** відкрити лист підтвердження в **іншому** браузері → на `/login` показується банер «Не вдалося підтвердити пошту…» (без `code` в адресному рядку).
15. **Невідомий маршрут:** `/some/unknown` → редірект на `/` (не порожня сторінка).
16. **Відновлення після logout+reload:** після успішного виходу перезавантажити сторінку → сесія не «воскресає».
